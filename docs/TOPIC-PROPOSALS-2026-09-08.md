# 유저 토픽 제안 구현 · 2026-09-08

월드에서 유저가 질문을 제안하고, 관리자가 검토한 뒤 기존 토픽 피드에 게시하는 1차 기능이다. 기존 작업 중인 변경사항은 유지했다.

## 사용자 흐름

- 월드 헤더의 **토픽 제안** → 내 제안·심사 알림 → **새 제안**.
- 질문 5~80자, 배경 설명 10~200자, 카테고리, 논의/뉴스 종류, 출처, 0점/100점 기준을 작성한다.
- 뉴스·사건에는 HTTPS 출처가 필수다. 점수 기준은 서로 달라야 하고 각 20자 이하다.
- 제목 입력 시 기존 공개 토픽을 검색해 참여 경로를 제공한다. 현재 부분 문자열 검색이며 의미 기반 중복 탐지는 아니다.
- 미리보기 → 커뮤니티 가이드 동의 → 검토 요청. 앱의 기존 가이드 버전 1.0 동의를 서버에서도 확인한다.
- 최근 **24시간** 최대 2건, 검토 중·수정 요청 합계 최대 3건. 철회해도 24시간 제출량은 복원하지 않는다.
- 검토 전 수정·철회 가능. 수정 요청을 받은 뒤 내용을 바꾸어 다시 제출하면 검토 중으로 돌아간다.
- 게시·수정 요청·반려·중복 연결 결과는 **앱 내 심사 알림**으로 저장된다. APNs 푸시는 포함하지 않는다.
- 게시 및 중복 연결 알림에서 실제 공개 토픽으로 이동한다. 숨김·차단된 토픽은 열 수 없다.

## 관리자 흐름

월드 토픽 페이지에 유저 제안 큐와 토픽 신고 큐를 추가했다.

- 승인: 제안 내용 그대로 토픽 + 단일 `match` 채점 대상 생성.
- 수정 요청·반려: 사유 필수. 제안자에게 결과 전달.
- 중복 연결: 사유와 기존 공개/마감 토픽 선택 필수. 새 토픽은 생성하지 않는다.
- 심사 중 작성자가 수정한 경우 revision 검증으로 오래된 내용의 승인을 거절한다.
- 신고: 토픽 숨김 및 처리 / 문제없음. 숨김과 신고 상태 변경을 한 트랜잭션으로 처리한다.
- 기존 토픽 관리에도 숨김 상태와 동작을 추가했다. 마감은 읽기 가능, 숨김은 공개 조회와 참여 차단이다.

현재 심사 목록은 최근 200건, 신고 목록은 오래된 미처리 200건까지 표시한다. 운영량이 늘면 관리자 서버 검색·페이지네이션을 확장해야 한다.

## 데이터와 권한

새 마이그레이션: `supabase/migrations/20260908000002_topic_submissions.sql`.

- `topic_submissions`: 작성자 본인만 SELECT. 직접 INSERT/UPDATE/DELETE 권한은 제거하고 제출·철회 RPC만 허용한다.
- `topic_submission_notifications`: 본인만 SELECT, `read_at` 컬럼만 UPDATE. 알림 내용과 수신자는 변경할 수 없다.
- 제출 시 계정 행 잠금으로 동시 요청의 한도 우회를 방지하고, 동일 제안 UUID 재시도는 중복 생성하지 않는다.
- 승인·제안 상태 변경·알림 생성은 하나의 DB 트랜잭션이다. 승인 재시도는 기존 결과를 반환한다.
- 심사 및 신고 처리 RPC는 service_role 전용이다. 관리자 API는 기존 세션·요청 출처 검사를 통과해야 한다. 검토자 이메일은 서버 세션에서 얻는다.
- 공개 topics에 origin, proposed_by, 출처와 점수 기준을 저장한다. 심사자 정보는 공개 토픽에 노출하지 않는다.
- 신고 target_type에 `topic` 추가. 차단한 제안자의 토픽은 피드와 직접 조회에서 제외한다.
- 숨긴 토픽은 피드·집계·반응에서 제외하고, 캐시된 상세에서의 점수 작성/수정도 서버에서 차단한다.
- 참여가 있는 커뮤니티 토픽의 질문·설명·점수 기준은 DB에서 변경을 차단한다.

기존 topics_feed 컬럼 순서를 유지하고 새 컬럼은 뒤에 추가했다. 앱 모델은 새 선택 컬럼이 없는 이전 응답도 해석할 수 있다.

## 기존 월드 개선

- 서버 토픽 상세의 설명·출처·제안자·점수 기준을 실제 데이터로 표시한다.
- 서버 연결 시 시드의 스포츠 메타데이터·지역 수치·반응을 대신 표시하지 않는다. 실데이터 지역 비교와 복수 채점 대상 설정은 별도 확장 범위다.
- 점수 작성 성공 후 서버 집계를 다시 읽는다. 서버 실패를 성공 피드백으로 표시하지 않는다.
- 토픽 신고 및 제안자 차단을 기존 신고 시트에 연결했다. 신고 권한 오류는 중복 신고로 오인하지 않는다.
- 공개 토픽 목록에 검색과 50건 단위 더 보기를 추가했다. 검색은 최대 20건을 반환한다.

## 검증

- iOS 시뮬레이터 빌드 성공.
- `TopicProposalTests` 3개 + `RemoteDecodingTests` 10개: 13개 통과.
- 새 임시 PostgreSQL DB에 전체 마이그레이션 적용 후 `supabase/tests/topic_submissions.sql`: 27개 검증 통과.
- DB 검증: 동의 필요, 본인만 조회, 직접 승인 금지, 서비스 전용 RPC, 중복 승인/알림 방지, 오래된 revision 거부, 제출/대기 제한, 뉴스 출처, 제재 계정, 수정 요청, 반려, 중복 연결, 철회, 신고 숨김, 차단, 숨김 후 채점 차단.
- 관리자 TypeScript 및 변경 경로 ESLint 통과. 원본 `.next`에는 기존 중복 타입 파일이 있어 별도 임시 타입 설정으로 확인했다.
- 원본 소스를 별도 임시 디렉터리로 복사한 깨끗한 환경에서 Next.js production build 성공.
- `admin/tests/topic-api-smoke.mjs`: 로컬 서버에 대해 14개 인증·출처·입력 검증 통과.
- 브라우저: 테스트 데이터로 로그인 → 제안 승인 → 공개 토픽 목록 갱신, 신고 숨김 → 목록 갱신 확인. 브라우저 오류 없음. 데스크톱/390px 모바일 배치 확인.
- 브라우저 테스트는 `admin/tests/topic-fixtures.mjs`의 격리된 fixture를 사용했다. 운영 Supabase를 통한 전체 앱↔관리자 실연동 검증은 수행하지 않았다.

## 적용 순서

1. 운영 환경에서 선행 마이그레이션 적용 여부를 확인한 뒤 새 DB 마이그레이션 적용.
2. 관리자 웹 배포 후 제안 조회·승인·신고 처리 확인.
3. 앱 빌드 배포 후 실제 테스트 계정으로 제안 → 승인 → 알림 → 점수 작성 확인.

이번 작업에서는 코드와 로컬 검증까지 완료했다. 운영 DB 적용·웹 배포·앱 배포는 하지 않았다. 공개 제안 게시판, 추천 투표, 유저 즉시 게시, APNs 알림, 자동 의미 기반 중복 판별은 포함하지 않는다.
