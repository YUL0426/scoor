`docs/P0-RELEASE-BLOCKERS.md`는 P0 10건을 전부 ✅로 표시하지만, 서버가 필요한
항목은 **기기 로컬 우회**로 처리된 것이었다.

| 항목 | 당시 처리 | 실제 상태 |
|---|---|---|
| P0-2 이메일 가입 | Keychain + PBKDF2 | 기기 안에만 존재하는 계정 |
| P0-7 기록 고아화 | 이메일 해시 → 결정적 UUID | 같은 기기에서만 복원 |

### 2.2 검증 중 발견해 고친 결함 3건

이 결함들은 SQL을 실제로 돌려보지 않았다면 코드 리뷰로는 드러나지 않았을 것들이다.

1. **LWW가 서버에서 강제되지 않았다.** PostgREST의 upsert(`merge-duplicates`)는
   조건 없이 덮어쓴다. 기기 A가 비행기 모드에서 쌓아둔 **오래된** 쓰기를 나중에
   올리면, 기기 B가 그 사이에 기록한 **최신** 값을 덮어써 사용자가 방금 쓴 점수가
   조용히 사라진다. → `scores_lww` BEFORE UPDATE 트리거로 서버가 거부하게 했다.
2. **집계 뷰가 draft 토픽을 노출했다.** 뷰는 소유자 권한으로 실행되어 기저 테이블
   RLS를 우회한다. 어드민이 작성 중인 토픽의 집계가 앱에 샐 수 있었다.
   → 뷰 안에 `status in ('live','closed')` 필터를 직접 넣었다.
3. `count(ws.*)` 모호성 → `count(ws.id)`.

### 3.1 배포가 잡아낸 결함 — GRANT 누락

적용 직후 **모든 테이블이 401**을 반환했다.

```
{"code":"42501","message":"permission denied for table topics",
 "hint":"Grant the required privileges to the current role with: GRANT SELECT ON public.topics TO anon;"}
```

원인: 0001~0003이 RLS만 켜고 **테이블 GRANT를 주지 않았다.** 접근에는 두 겹이
모두 필요하다 — `GRANT`가 "이 롤이 이 테이블을 건드릴 수 있는가"(거친 문),
`RLS`가 "그중 어떤 행을 볼 수 있는가"(촘촘한 체). 문이 잠겨 있으면 체는 의미가 없다.

> **이 결함을 로컬 검증이 놓친 이유가 중요하다.** 로컬 테스트 하네스가
> `grants_shim.sql`로 전 테이블에 권한을 뿌리고 시작했다. 편의를 위해 넣은 그
> 한 줄이 실제 프로덕션 구멍을 정확히 가렸다. 스키마 논리는 로컬에서 증명되지만,
> **권한 설정은 배포된 프로젝트에서만 증명된다.**

→ `20260719000004_grants.sql`로 수정. 향후 테이블이 같은 구멍에 빠지지 않도록
`ALTER DEFAULT PRIVILEGES`도 함께 설정했다.

## 4. 실서버 E2E 검증 완료 ✅ (14/14)

`supabase/tests/e2e_rls.sh` — 앱이 호출하는 것과 동일한 PostgREST/GoTrue
엔드포인트를 실제 JWT로 두드린다.

| 영역 | 검증 항목 | 결과 |
|---|---|---|
| 계정 | SQL 생성 계정이 GoTrue password grant로 로그인 | PASS |
| 트리거 | 가입 시 프로필 자동 생성 | PASS |
| RLS | A가 자기 점수를 읽음 / **B는 A의 점수를 볼 수 없음** | PASS |
| RLS | B가 A의 계정에 쓰기 시도 → 42501 차단 | PASS |
| LWW | 오래된 쓰기(09:00) 무시 / 최신 쓰기(11:00) 반영 | PASS |
| 복원 | **재로그인 후 기록이 그대로 복원** (P0-7의 실제 해결) | PASS |
| 권한 | 익명 토픽 읽기 허용 / 사용자 토픽 생성 차단 | PASS |
| 신고 | 삽입 가능, 신고자 조회 불가 | PASS |
| 삭제 | 계정 삭제 시 점수까지 CASCADE (완전 삭제 정책) | PASS |

### 4.1 이 실행이 잡아낸 것 — "가짜 통과"

첫 실행에서 LWW 테스트가 통과했지만 **이유가 틀렸다.** 스크립트가 scores
upsert에 `on_conflict=user_id,day`를 붙이지 않아, `unique(user_id, day)`가
PK가 아닌 탓에 두 번째 쓰기가 그냥 제약 위반으로 실패하고 있었다. 값이 안
바뀐 것을 "트리거가 막았다"고 읽은 것이다.

파라미터를 붙이자 "최신 쓰기 반영"이 함께 통과하면서, 비로소 트리거가 실제로
오래된 쓰기만 골라 거부한다는 것이 증명됐다. **앱 코드는 처음부터 옳았다** —
`SupabaseRequest.upsert`가 `on_conflict`를 보내고 있었고, 틀린 쪽은 검증
스크립트였다.

### 4.2 테스트 계정 처리

GoTrue 가입 대신 SQL로 계정을 만든다. 가입 엔드포인트는 확인 메일을 보내려
하고 무료 티어 SMTP 한도에 즉시 걸려 반복 실행이 불가능하기 때문이다. 이
방식은 **프로덕션의 `Confirm email` 설정을 끌 필요가 없다** — 검증 편의를 위해
인증을 약화시키지 않는다. 비밀번호는 GoTrue와 같은 bcrypt로 저장되므로 이후
로그인은 실제 인증 경로를 그대로 탄다.

실행 후 테스트 계정을 삭제하며, 삭제 자체가 CASCADE 검증을 겸한다.
검증 종료 시점 서버 잔여물: **users 0 / scores 0 / profiles 0 / reports 0.**

## 7. 결론

**서버 계층은 검증되었다.** 마이그레이션이 실서버에 적용됐고, 로컬 20건 +
실서버 14건으로 RLS 격리·LWW·재로그인 복원·CASCADE 삭제를 확인했다.
클라이언트는 빌드 성공 + 74 유닛 테스트 통과.

검증 과정이 세 종류의 결함을 드러냈고, 각각 다른 층에서만 잡혔다:

1. **로컬 실행**이 잡은 것 — LWW 미강제, 뷰의 draft 누출 (코드 리뷰로는 안 보임)
2. **배포**가 잡은 것 — GRANT 누락 (로컬 하네스가 권한을 뿌려 가리고 있었음)
3. **실서버 E2E**가 잡은 것 — 검증 스크립트의 "가짜 통과" (제약 위반을 트리거
   동작으로 오독)

**Phase 1 전체는 미완료로 보고한다.** 서버는 준비됐지만 앱 UI가 아직 World와
신고·차단에 연결되지 않았고, 이 둘은 App Store Guideline 1.2 때문에 반드시
함께 나가야 한다. 남은 항목은 §6.
