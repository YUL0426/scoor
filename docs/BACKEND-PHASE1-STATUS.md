### 2.2 검증 중 발견해 고친 결함 3건

이 결함들은 SQL을 실제로 돌려보지 않았다면 코드 리뷰로는 드러나지 않았을 것들이다.

1. **LWW가 서버에서 강제되지 않았다.** PostgREST의 upsert(`merge-duplicates`)는
   조건 없이 덮어쓴다. 기기 A가 비행기 모드에서 쌓아둔 **오래된** 쓰기를 나중에
   올리면, 기기 B가 그 사이에 기록한 **최신** 값을 덮어써 사용자가 방금 쓴 점수가
   조용히 사라진다. → `scores_lww` BEFORE UPDATE 트리거로 서버가 거부하게 했다.
2. **집계 뷰가 draft 토픽을 노출했다.** 뷰는 소유자 권한으로 실행되어 기저 테이블
   RLS를 우회한다. 어드민이 작성 중인 토픽의 집계가 앱에 샐 수 있었다.
   → 뷰 안에 `status in ('live','closed')` 필터를 직접 넣었다.
3. `count(ws.*)` 모호성 → `count(ws.id)`.

### 3.1 배포가 잡아낸 결함 — GRANT 누락

적용 직후 **모든 테이블이 401**을 반환했다.

```
{"code":"42501","message":"permission denied for table topics",
 "hint":"Grant the required privileges to the current role with: GRANT SELECT ON public.topics TO anon;"}
```

원인: 0001~0003이 RLS만 켜고 **테이블 GRANT를 주지 않았다.** 접근에는 두 겹이
모두 필요하다 — `GRANT`가 "이 롤이 이 테이블을 건드릴 수 있는가"(거친 문),
`RLS`가 "그중 어떤 행을 볼 수 있는가"(촘촘한 체). 문이 잠겨 있으면 체는 의미가 없다.

> **이 결함을 로컬 검증이 놓친 이유가 중요하다.** 로컬 테스트 하네스가
> `grants_shim.sql`로 전 테이블에 권한을 뿌리고 시작했다. 편의를 위해 넣은 그
> 한 줄이 실제 프로덕션 구멍을 정확히 가렸다. 스키마 논리는 로컬에서 증명되지만,
> **권한 설정은 배포된 프로젝트에서만 증명된다.**

→ `20260719000004_grants.sql`로 수정. 향후 테이블이 같은 구멍에 빠지지 않도록
`ALTER DEFAULT PRIVILEGES`도 함께 설정했다.

### 4.1 이 실행이 잡아낸 것 — "가짜 통과"

첫 실행에서 LWW 테스트가 통과했지만 **이유가 틀렸다.** 스크립트가 scores
upsert에 `on_conflict=user_id,day`를 붙이지 않아, `unique(user_id, day)`가
PK가 아닌 탓에 두 번째 쓰기가 그냥 제약 위반으로 실패하고 있었다. 값이 안
바뀐 것을 "트리거가 막았다"고 읽은 것이다.

파라미터를 붙이자 "최신 쓰기 반영"이 함께 통과하면서, 비로소 트리거가 실제로
오래된 쓰기만 골라 거부한다는 것이 증명됐다. **앱 코드는 처음부터 옳았다** —
`SupabaseRequest.upsert`가 `on_conflict`를 보내고 있었고, 틀린 쪽은 검증
스크립트였다.

### 4.2 테스트 계정 처리

GoTrue 가입 대신 SQL로 계정을 만든다. 가입 엔드포인트는 확인 메일을 보내려
하고 무료 티어 SMTP 한도에 즉시 걸려 반복 실행이 불가능하기 때문이다. 이
방식은 **프로덕션의 `Confirm email` 설정을 끌 필요가 없다** — 검증 편의를 위해
인증을 약화시키지 않는다. 비밀번호는 GoTrue와 같은 bcrypt로 저장되므로 이후
로그인은 실제 인증 경로를 그대로 탄다.

실행 후 테스트 계정을 삭제하며, 삭제 자체가 CASCADE 검증을 겸한다.
검증 종료 시점 서버 잔여물: **users 0 / scores 0 / profiles 0 / reports 0.**

### 6.1 설정 화면 (spec-13 C7)

동기화 섹션은 백엔드가 프로비저닝된 빌드에서만 나타나고, 표시하는 것은 마지막
성공 시각 하나뿐이다. 관리해야 할 기능처럼 보이면 안 된다 — 동기화가 실패했든
성공했든 저널링은 그대로 동작하기 때문이다. 탭하면 수동 동기화.

차단 목록은 해제까지 제공한다. 차단만 있고 해제가 없으면 되돌리는 유일한 방법이
문의 메일이 된다. 해제는 낙관적 업데이트(실패 시 행 복원).

### 6.2 로컬 → 서버 마이그레이션 — 발견한 결함

이 항목은 "아직 안 만든 기능"이 아니라 **사용자에게 데이터 손실로 보이는 버그**
였다. 게스트로 기록한 뒤 로그인하면:

- 로그인이 계정 id를 서버 `auth.users.id`로 바꾸는데, 로컬 `ScoreModel` 행은
  이전 기기 UUID에 그대로 묶여 있었다.
- 모든 화면이 *현재* id로 조회하므로 **캘린더·홈·통계가 빈 화면**이 된다.
  디스크에는 남아 있지만 사용자 입장에서는 기록이 사라진 것과 구별되지 않는다.
- 그 기록은 서버에도 영원히 올라가지 않는다 (P0-7이 실제로는 안 풀린 상태).

방명록도 같은 결함을 공유했다(`recipientId`가 로그인 전 id).

`AccountMigrator`가 계정당 한 번 실행되며, 중요도 순으로 3단계다:

1. **로컬 재키잉** (점수 + 방명록) — 네트워크 불필요, 유실 불가.
2. **아웃박스 적재** — 오프라인 로그인도 나중에 백업된다.
3. **프로필 업로드** (닉네임/이모지/bio → `profiles`) — 유일하게 실패해도 되는
   단계. 재시도용 플래그를 따로 둔다.

두 가지를 특히 조심해서 처리했다:

- **업로드 시각을 위조하지 않는다.** 과거 기록을 `now`로 스탬프해 올리면 한 달 전
  기록이 "가장 최신 쓰기"가 되어, 다른 기기에서 한 시간 전에 고친 값을 서버 LWW가
  덮어쓴다. 백필은 각 행의 원래 `createdAt`을 보낸다.
- **날짜 충돌 시 최신 쪽을 남긴다.** 두 번째 기기에서 계정이 이미 그 날짜를 갖고
  있으면, 더 최근에 쓴 쪽만 살린다 — 앱이 이미 지키는 "하루 1점수, 마지막 쓰기
  승리" 규칙과 동일하므로 사용자 정신모델이 바뀌지 않는다.

### 6.3 어드민 토픽 큐레이션

`/admin/topics` + `/api/topics`. 서비스 롤 키는 서버 전용(`NEXT_PUBLIC_` 접두사
없음)이고, 미설정 시 mock으로 폴백하지 않고 503을 준다 — 운영 도구가 가짜 토픽을
보여주면 진짜 토픽이 아무에게도 발행되지 않는다.

`proxy.ts`의 matcher는 페이지 경로만 덮으므로(`/`, `/admin/:path*`, `/login`)
**API 라우트는 각자 세션을 검사**해야 한다. 없으면 인증 없는 POST 한 번으로 전
사용자에게 토픽이 발행된다 → `requireAdmin()`.

새 토픽은 `draft` 기본값이고 발행은 별도 클릭이다. draft는 `topics_feed`가
걸러내므로 작성 중인 토픽이 앱에 새지 않는다. 수정 가능한 필드는 상태뿐 —
이미 점수가 매겨진 토픽의 제목을 바꾸면 그 점수의 의미가 달라진다.

`status`만 바꾸는 이유와 별개로, 화면은 "오늘 live 3개 미만"을 경고한다
(spec-13 §15-4: 일 3~5개).

1. **로컬 실행**이 잡은 것 — LWW 미강제, 뷰의 draft 누출 (코드 리뷰로는 안 보임)
2. **배포**가 잡은 것 — GRANT 누락 (로컬 하네스가 권한을 뿌려 가리고 있었음)
3. **실서버 E2E**가 잡은 것 — 검증 스크립트의 "가짜 통과" (제약 위반을 트리거
   동작으로 오독)

**Phase 1 코드 작업은 완료로 보고한다.** 서버가 검증됐고, 앱은 World를 실제
토픽에서 읽으며 신고·차단·가이드라인이 함께 들어갔다(Guideline 1.2). 로그인 시
로컬 기록 인수까지 붙어 P0-7이 비로소 실제로 해결됐다.

마무리 과정에서 두 가지를 더 잡았다:

4. **정적 검증이 잡은 것** — 로컬→서버 인수 자체가 빠져 있었다(§6.2). 서버는
   14/14로 통과했는데도 게스트가 로그인하면 캘린더가 비었다. 서버 검증은 서버가
   옳은지만 증명하고, 그 데이터가 서버에 도달하는지는 증명하지 않는다.
5. **시간이 잡은 것** — `testFreshTakesPriorityOverDeltaForNewTopics`가 고정
   타임스탬프로 "6시간 이내" 규칙을 검증해, 작성한 날 하루만 통과하고 다음 날부터
   영구 실패했다. 상대 시간 규칙은 픽스처도 상대적이어야 한다.

**남은 것은 코드가 아니다** — Apple/Google provider 설정, Edge Function 배포,
어드민 env 주입은 계정 권한이 필요한 작업이다(§6.4).
