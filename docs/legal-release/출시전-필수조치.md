# Scoor 개인정보처리방침 — 출시 전 필수 조치

검토일: 2026년 9월 9일

이 문서는 운영자용입니다. 공개할 개인정보처리방침에 붙여 넣지 않습니다. 앱 구현은 현재 로컬 작업본을 기준으로 확인했으며, 운영 DB에 마이그레이션이 적용됐는지와 실제 출시 빌드의 동작은 별도 확인이 필요합니다. 심사 결과나 법적 무결성을 보증하는 의견서는 아닙니다.

## 확인된 운영 정보

- 운영자 및 개인정보 담당자: **YUL HEO**. 운영자가 직접 문의를 처리하는 1인 운영 구조로 작성했습니다.
- 문의 이메일: **officialscoor@gmail.com**. 사용자 확인을 반영했으며, 실제 수신·회신 시험은 하지 않았습니다.
- 출시 범위: 주요 20개국을 고려 중이며 정확한 목록은 미정입니다. 국가를 임의로 지정하지 않았습니다.
- 연령: 사용자는 가능한 최소 제한을 원합니다. 보호자 동의 없이 전 연령을 받는 운영으로 확정하지 않았습니다.
- Supabase: 사용자 로그인 후 `officialscoor@gmail.com` 조직의 Free 플랜을 확인했습니다. 앱의 `SUPABASE_HOST`와 `scoor` 프로젝트(`ebxdbadcejbytixumxrj`)가 일치하며 주 DB 리전은 서울(ap-northeast-2)입니다. 같은 조직의 `Scoor-old`와 구분했습니다.
- 백업: 예약 백업 화면은 Free 플랜 미포함, PITR 화면은 Pro 추가 기능으로 표시됩니다. 현재 이 두 기능을 사용하지 않습니다. 수동 백업이나 제공자 내부 사본의 부재까지 확인한 것은 아닙니다.
- 로그: 실제 API Gateway 로그에서 요청 시각·메서드·경로·상태코드를 확인했습니다. Free 플랜의 API·DB 플랫폼 로그 표준 보유기간은 1일입니다. Auth 감사 테이블·별도 보안기록 등 모든 종류에 1일을 적용하지 않습니다. [Supabase 플랜별 로그 보유기간](https://supabase.com/pricing)
- 인증메일: Authentication → Emails → SMTP Settings의 custom SMTP 스위치가 꺼져 있습니다. 별도 Send Email Hook 사용 여부는 추가 확인 대상입니다. 일반 이용자에게 인증메일을 보내려면 실제 발송 경로와 외부 수신자 발송을 검증해야 합니다. 기본 SMTP는 팀에 등록된 주소로 발송이 제한되는 시험용 서비스입니다. 발송 제공자를 추가하면 위탁·국외 이전 표도 함께 갱신하세요. [Supabase SMTP 안내](https://supabase.com/docs/guides/auth/auth-smtp)

### 운영 DB와 로컬 코드의 차이

2026년 9월 9일 대시보드의 Database Migrations 목록에는 `20260822000007 feed`까지 7개가 표시됩니다. 로컬의 `20260908000001_daily_score_home_sharing.sql`, `20260908000002_topic_submissions.sql`은 해당 이력에 보이지 않습니다. 수동 SQL로 일부 반영했을 가능성은 별도 확인이 필요하지만, 최신 기능의 운영 적용을 완료했다고 확정할 수 없습니다. **현재 방침의 토픽 제안·검토 알림 부분은 로컬 출시 후보 구현 기준이며 운영 적용과 실제 출시 기능을 먼저 일치시켜야 합니다.**

개요 화면에는 `Unhealthy` 상태와 `topic_stats`, `topic_region_stats`, `topics_feed`의 SECURITY DEFINER 뷰 경고도 표시됐습니다. 이 표시만으로 개인정보 노출을 확정할 수는 없으나, 출시 전 서비스 상태와 해당 뷰의 RLS·공개범위를 확인해야 합니다. 이 확인 과정에서는 운영 데이터나 설정을 변경하지 않았습니다.

개인정보 담당 부서, 법인, 별도 법무팀을 가상으로 만들지 않았습니다. 전화번호도 임의로 추가하지 않았습니다. 다만 개인정보 보호법 제30조의 책임자 및 연락처 기재 요건과 출시 국가의 연락수단 요건을 검토하여, 이메일 외 업무용 연락처가 필요한 범위는 게시 전에 보완해야 합니다. 자택 주소를 임의로 공개할 필요는 없으며, 해외에서는 별도의 사업자·컨트롤러 연락정보 고지 요건을 확인해야 합니다. [국가법령정보센터 제30조](https://www.law.go.kr/LSW/lsLinkCommonInfo.do?chrClsCd=010202&lsJoLnkSeq=1025127653)

## 먼저 해결할 네 가지

### 1. 삭제를 약속하는 내용과 실제 동작을 맞추기

**확인한 문제**

- `RemoteScoreService.swift`의 삭제 동기화는 이유·감정 값을 비우지만 점수·날짜·계정 식별자 등은 남깁니다.
- `RemoteFeedService.swift`의 댓글 삭제와 홈 공유 해제는 본문을 지우지 않고 `deleted_at`만 설정합니다.
- `MyPageViewModel.deleteScore(for:)`는 개인 기록 서비스만 호출합니다. 이미 게시된 홈 공유 글을 함께 삭제하는 호출은 없습니다.
- `withdraw_topic_proposal`은 철회 상태만 기록하고 내용을 유지합니다.
- `topics.proposed_by`는 `on delete set null`입니다. 탈퇴해도 승인된 토픽 제목·설명·출처 등은 남으며, 본문의 개인정보까지 익명화되는 것은 아닙니다.
- 읽은 코드와 마이그레이션에서 삭제 표시 데이터의 정기 완전 파기 작업은 확인하지 못했습니다.

**출시 전 필요한 결과**

1. 개인 기록 삭제 시 연결된 홈 게시물의 처리까지 연결하고, 실패하면 성공으로 안내하지 않도록 합니다. 삭제 전 공유 해제를 요구하는 현재 우회 안내는 문서에 반영했지만, 장기적인 해결책으로 삼지 않는 것이 좋습니다.
2. 삭제·공유 해제된 본문은 불필요한 내용이 남지 않도록 제거합니다. 신고 증거로 보관해야 하는 경우에는 실제 필요한 사건에 한정하여 근거·항목·기한·접근 권한을 정합니다. 전체 댓글을 탈퇴 때까지 보관하는 방식은 지양합니다.
3. 동기화용 삭제 표식은 콘텐츠와 분리하여 최소화하고 기한을 정합니다. 표식 제거 후 오래된 오프라인 기기가 데이터를 다시 업로드하는 문제도 처리해야 합니다. 임의로 30일 뒤 행을 삭제하는 작업만 추가하면 해결되지 않습니다.
4. 탈퇴 후 남는 승인 토픽은 개인 식별 내용까지 처리할 절차를 마련합니다. 법정 보존 필요가 없는 사용자 작성 콘텐츠의 삭제 범위를 Apple 기준과 맞추어 검증합니다.
5. 테스트 계정으로 개인 기록·홈 게시물·World 참여·댓글·제안·알림 생성 → 개별 삭제 → 탈퇴 → 다른 계정에서 열람 및 운영 DB 잔존 여부를 확인합니다. 실제 이용자의 계정이나 데이터로 시험하지 않습니다.

Apple은 계정 생성 기능이 있으면 앱 내 계정 삭제를 제공하고, 법적으로 보존해야 하는 경우를 제외한 관련 개인정보와 사용자 콘텐츠도 삭제하도록 안내합니다. “본문은 계속 보관한다”는 방침을 게시하는 것만으로 이 요건을 충족하지는 않습니다. [Apple 계정 삭제 안내](https://developer.apple.com/support/offering-account-deletion-in-your-app/)

**Apple 로그인 연결 해제도 확인:** `account-delete/index.ts`에는 토큰 폐기 시도가 있으나 실패해도 계정 삭제를 계속하고 `apple_revoked: false`를 반환할 수 있습니다. 계정 삭제 실패를 강제하기보다 폐기 실패를 추적·재처리할 수 있는 구조와 운영 설정을 검증해야 합니다. 방침에 “Apple 연결이 항상 즉시 해제된다”고 약속하지 않았습니다.

### 2. 민감정보에 대한 실제 처리 경로 정하기

정치 카테고리의 주제·찬반 점수는 계정과 연결될 때 정치적 견해를 드러낼 수 있습니다. 건강 관련 자유 입력도 내용에 따라 민감정보에 해당할 수 있습니다. 일상 점수 전체가 자동으로 건강정보가 되는 것은 아니지만, “의료 앱이 아니다” 또는 “입력에 주의하라”는 문장만으로 처리 근거가 생기지는 않습니다. 개인정보 보호법 제23조는 민감정보 처리에 별도 동의 또는 법령상 근거 등을 요구합니다. [개인정보 보호법](https://www.law.go.kr/LSW/lsInfoP.do?ancNo=19234&ancYd=20230314&ancYnChk=0&chrClsCd=010202&efGubun=Y&efYd=20240315&lsiSeq=248613&nwJoYnInfo=Y)

현재 확인된 것은 커뮤니티 가이드라인 동의입니다. 민감정보 별도 동의와 동일하지 않습니다.

**1인 개발자의 첫 출시에는 정치적 견해·건강 등 민감정보를 의도적으로 수집하는 토픽을 우선 제외하는 운영을 제안합니다.** 이는 이번에 적용한 변경이 아닙니다. 채택한다면 화면의 정치 카테고리만 숨기지 말고, 토픽 생성·제안·참여 API와 운영 검토에도 반영해야 합니다. 일반 자유 입력란에서 민감정보가 접수되는 경우의 대응 절차도 마련해야 합니다.

해당 기능을 유지하려면 별도 동의 화면에 실제 항목, 목적, 보유기간, 거부권과 제한되는 기능을 고지하고, 공개 가능성과 비공개 방법도 안내해야 합니다. 동의 이력·철회·삭제와 서버 측 검증까지 구현한 후 방침 제4항을 확정하세요. 동의를 거부해도 민감정보가 필요하지 않은 기본 기능은 사용할 수 있게 설계합니다. 공개에 별도 제공 동의 등 추가 근거가 필요한지도 실제 공개 방식에 맞춰 검토합니다.

### 3. 최소 연령과 출시 국가를 함께 확정하기

한국에서는 만 14세 미만 아동에 대해 이 법에 따른 동의가 필요한 개인정보 처리를 하려면 법정대리인 동의와 확인이 필요합니다. 현재 그 절차는 확인되지 않습니다. 따라서 **한국 출시의 운영 제안은 만 14세 이상**입니다. 이는 14세가 모든 서비스의 보편적인 가입 허용 연령이라는 뜻은 아닙니다. [개인정보 보호법 제22조의2](https://law.go.kr/LSW/lsLinkCommonInfo.do?chrClsCd=010202&lsJoLnkSeq=1006183947)

해외 20개국에 동일한 최소 연령이 통한다고 단정할 수 없습니다. EU에서 아동에게 온라인 서비스를 제공하면서 동의를 근거로 개인정보를 처리하는 경우, 국가별 보호자 동의 기준은 13~16세입니다. 미국 COPPA는 아동 대상 서비스 또는 13세 미만 이용자의 정보를 수집한다는 사실을 실제로 아는 일반 대상 서비스 등에 적용됩니다. 두 제도 모두 단순히 약관에 숫자 하나를 쓰는 것으로 충족되지 않습니다. [EU 집행위원회](https://commission.europa.eu/law/law-topic/data-protection/information-business-and-organisations/legal-grounds-processing-data/are-there-any-specific-safeguards-data-about-children_en), [미국 FTC](https://www.ftc.gov/business-guidance/resources/complying-coppa-frequently-asked-questions)

최소 제한을 원하는 경우, App Store 출시 국가 목록을 먼저 정하고 국가별 가입·동의 기준을 매핑하는 방식이 적합합니다. 국가별 처리가 부담된다면 16세 이상 단일 기준을 검토할 수 있지만, **16세 역시 모든 국가의 미성년자·SNS 관련 법을 일괄 충족하는 보장은 아닙니다.** 해외 출시는 현지 권리 고지, 민감정보, 국외 이전, 대표자 지정 필요성 등을 추가 확인해야 합니다.

연령 확인은 최초 개인정보 수집·전송 전에 배치하고, 불필요한 생년월일 전체 저장은 피합니다. 현재 코드에는 연령 확인 절차가 없으므로 이를 시행 중인 것처럼 방침에 쓰지 않았습니다. App Store 콘텐츠 연령 등급도 개인정보 동의 및 가입 절차를 대신하지 않습니다.

**한국 만 14세 이상 제한을 실제 적용한 뒤 사용할 문안:**

> Scoor는 만 14세 이상 이용자를 대상으로 하며 만 14세 미만의 회원가입을 허용하지 않습니다. 연령 기준에 미달하는 아동의 개인정보가 처리된 사실을 확인하면 필요한 확인을 거쳐 해당 정보의 처리를 중단하고 지체 없이 삭제합니다. 관련 요청은 officialscoor@gmail.com으로 접수할 수 있습니다.

해외 범위는 확정된 국가별 절차에 맞춰 별도 보완해야 합니다. 이 문안은 미구현 상태에서 바로 게시하는 문안이 아닙니다.

### 4. Supabase·Gmail의 처리 위치와 보유기간 확인하기

기존 웹페이지 문구에만 의존하지 않고, 로그인 후 대시보드와 앱 호스트를 대조하여 서울 리전을 확인했습니다. Supabase DPA는 지정 리전의 주된 저장·처리와 추가 지시·서비스 제공 등을 위한 처리 조건을 구분합니다. 국내 DB 리전만 확인해서 국외 이전이 없다고 쓰면 안 됩니다. [Supabase DPA](https://supabase.com/legal/customer-resources/data-processing-addendum)
